## Context

В проекте уже реализован materialized слой `session_metrics` и backend contract
`query_project_metrics`, который возвращает агрегированные project metrics и хронологический список
`SessionMetrics` для заданного `project_key` и временного диапазона. Текущий frontend показывает
метрики в основном только на уровне выбранной сессии через `SessionMetricsPanel`; отдельного
project-level экрана и графического представления трендов пока нет.

Из-за этого аналитика по проекту остаётся скрытой внутри JSON-like payload и единичных карточек.
Пользователю нужен отдельный экран, на котором можно переключаться между проектами и видеть
хронологические графики по разным метрикам без ручного обхода десятков сессий.

## Goals / Non-Goals

**Goals:**

- Дать отдельный project-level экран в `codex-session-explorer`.
- Построить хронологические графики по нескольким метрикам на основе уже существующего
  `ProjectMetricsResponse`.
- Поддержать project selector, временной диапазон и toggle `include_spawn_agents`.
- Сохранить связь графиков с contributing sessions и переходом к конкретной сессии.
- Явно визуализировать `known`/`partial`/`unknown` coverage и degraded project state.

**Non-Goals:**

- Не переписывать слой `session_metrics` или storage contract с нуля.
- Не строить произвольный BI-конструктор с настраиваемыми формулами и дашборд-редактором.
- Не вводить серверную агрегацию по произвольным bucket size, если первого слоя достаточно на
  уровне point-per-session chronology.
- Не заменять существующую session-level panel: новый экран дополняет её, а не удаляет.

## Decisions

### 1. Экран строится поверх уже существующего `ProjectMetricsResponse`

Решение: использовать `query_project_metrics` как единственный источник данных для графиков, а
серии строить во frontend из `sessions[]` и project-level aggregate payload.

Причина: backend уже возвращает хронологический список `SessionMetrics` и итоговые агрегаты. Это
позволяет быстро добавить экран без нового persistence-слоя и без второго вычислителя метрик.

Альтернатива: добавить отдельный API с готовыми chart series. Это уменьшит код во frontend, но
сейчас расширяет контракт без явной необходимости.

### 2. Project selector собирается из известных session catalog записей

Решение: формировать список доступных проектов из загруженного indexed session catalog, группируя
записи по `project_key`/`cwd`/git metadata и исключая дубликаты.

Причина: отдельного project catalog API пока нет, а frontend уже читает session catalog. Для
первого шага этого достаточно, чтобы выбрать проект и не вводить лишний backend surface.

Альтернатива: добавить отдельную backend команду list-projects. Это может понадобиться позже для
масштабирования, но сейчас выходит за рамки change.

### 3. Первый набор графиков фиксированный и отражает практические деградации

Решение: в первой версии показать набор time-series карточек/графиков для:

- `duration.total_ms`;
- `token_ledger.total`;
- `error_count` и `operations.failed_operations`;
- `operations.tool_calls`;
- число сессий в хронологии.

Причина: это самый полезный слой для поиска деградаций стоимости, времени и стабильности. Он
напрямую соответствует уже существующему metrics contract.

Альтернатива: строить графики для всех metric groups сразу. Это перегружает экран и размывает
первый пользовательский сценарий.

### 4. Unknown и partial coverage остаются видимыми на графике и в tooltip

Решение: если метрика имеет `unknown`, точка не интерполируется как ноль; график показывает gap
или специальный marker, а tooltip явно сообщает coverage/source. Для `partial` отображается число
с пометкой о неполном покрытии.

Причина: главная ловушка аналитического UI здесь в том, что отсутствие данных легко принять за
улучшение. Экран должен сохранять семантику metrics contract.

Альтернатива: приводить `unknown` к `0` ради более ровных графиков. Это искажает данные.

### 5. Экран остаётся тесно связан с session explorer workflow

Решение: каждая точка графика и каждая строка contributing sessions открывает соответствующую
сессию в текущем explorer без отдельного окна и без разрыва контекста.

Причина: цель экрана не только показать тренд, но и дать быстрый drill-down к сессии, вызвавшей
спайк токенов, ошибок или времени.

Альтернатива: сделать dashboard полностью изолированным от session explorer. Это снижает пользу
для локального расследования деградаций.

### 6. Временное окно задаётся готовыми пресетами плюс произвольным диапазоном

Решение: поддержать пресеты вроде `7d`, `30d`, `90d` и ручной ввод start/end timestamp.

Причина: пресеты закрывают типовой сценарий, а ручной диапазон нужен для точечной диагностики
релизного окна или конкретного периода.

Альтернатива: только произвольные даты. Это медленнее и неудобнее для повседневного просмотра.

## Risks / Trade-offs

- [Risk] Session catalog может не содержать всех проектов, для которых уже лежат materialized
  metrics. -> Mitigation: в первом UI явно сообщать, что selector строится по доступным сессиям, и
  добавить backend project catalog позже при необходимости.
- [Risk] Большое число точек может перегрузить браузер при рендере графиков. -> Mitigation:
  начинать с point-per-session series без тяжёлых анимаций и при необходимости вводить downsampling.
- [Risk] Unknown/partial точки ухудшат визуальную гладкость графиков. -> Mitigation: это осознанная
  цена за честную визуализацию; дополнительно показать legend и tooltip с объяснением.
- [Risk] Degraded project buckets сложно интерпретировать пользователю. -> Mitigation: вынести
  явный banner с причиной degraded-state и не смешивать такие записи с нормальными проектами.

## Migration Plan

1. Добавить в frontend состояние/route для project metrics screen.
2. Реализовать project selector и фильтры диапазона поверх session catalog и query args.
3. Добавить визуальные series/графики и summary cards на базе `ProjectMetricsResponse`.
4. Подключить drill-down из графиков и contributing session list к текущему session explorer.
5. Добавить тесты для selector, query lifecycle, coverage-state rendering и переходов к сессиям.

Rollback: скрыть новый экран feature-level откатом frontend изменений; backend contract и storage
остаются совместимыми и не требуют миграции данных.
