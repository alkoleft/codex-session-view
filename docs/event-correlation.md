# Корреляция событий и связей между логами сессий

Этот документ фиксирует практическую модель связывания событий в `stdout.jsonl` и в логах сессий субагентов `subagents/<thread_id>.jsonl`.

Документ опирается на наблюдаемую структуру логов, а не на внутреннюю реализацию проекта.

## Цель

Нужно уметь:

- связывать события между разными файлами, когда один лог расширяет другой;
- связывать связанные операции внутри одного файла;
- отделять реальные операции от дублирующих представлений одного и того же события;
- хранить связь явно, а не восстанавливать её заново при каждом анализе.

## Базовые наблюдения

- `stdout.jsonl` обычно отражает внешний ход родительской сессии.
- Лог `subagents/<thread_id>.jsonl` отражает детальный ход дочерней сессии.
- Эти два лога образуют два связанных, но не тождественных слоя:
  - `stdout.jsonl` это в первую очередь `control-plane` orchestration-level события;
  - `subagents/<thread_id>.jsonl` это `session-detail` события уже внутри конкретной дочерней сессии.
- Имя файла лога субагента можно использовать как отдельный сигнал: basename файла совпадает с `session_id` и обычно совпадает с `thread_id` этой дочерней сессии.
- Родительский лог часто содержит агрегированные или сокращённые сообщения, а дочерний лог содержит детальные шаги и сырой вывод инструментов.
- Одного упоминания инструмента `spawn_agent` недостаточно для надёжной привязки к дочерней сессии. Для жёсткой связи нужен конкретный `thread_id`, обычно пришедший через `receiver_thread_ids`.
- В логе субагента могут встретиться записи из forked history родительской или чужой сессии. Поэтому не каждая строка session file автоматически относится к сессии, id которой стоит в имени файла.

## Основная модель

Рекомендуется хранить три набора данных:

- `entities`
- `events`
- `relations`

Не стоит пытаться заранее склеить всё в один канонический event. Один и тот же процесс обычно проявляется несколькими событиями, а связь между ними лучше хранить отдельно.

## Сущности

Минимальный набор сущностей:

- `session`
- `operation`
- `tool_call`
- `command`

Пример:

```json
{
  "entities": [
    {
      "id": "session:019d621d-620a-7d52-a76d-e45172a83603",
      "kind": "session",
      "thread_id": "019d621d-620a-7d52-a76d-e45172a83603",
      "source_file": "stdout.jsonl"
    },
    {
      "id": "session:019d621d-98e5-7da2-8c48-99a5267f1ad6",
      "kind": "session",
      "thread_id": "019d621d-98e5-7da2-8c48-99a5267f1ad6",
      "source_file": "subagents/019d621d-98e5-7da2-8c48-99a5267f1ad6.jsonl",
      "file_session_id": "019d621d-98e5-7da2-8c48-99a5267f1ad6"
    },
    {
      "id": "op:item_1",
      "kind": "operation",
      "tool": "spawn_agent"
    },
    {
      "id": "call:call_poY5PltBnP6YViNfQgpr5GzQ",
      "kind": "tool_call",
      "tool": "exec_command"
    },
    {
      "id": "cmd:ping-c-1-127.0.0.1",
      "kind": "command",
      "command": "ping -c 1 127.0.0.1"
    }
  ]
}
```

## События

Каждую строку лога полезно нормализовать в запись со стабильным идентификатором.

Рекомендуемый минимальный набор полей:

- `id`
- `source_file`
- `line`
- `raw_type`
- `ts`
- `session_id`
- `thread_id`
- `item_id`
- `call_id`
- `tool`
- `status`
- `prompt`
- `message`
- `arguments`
- `receiver_thread_ids`

Примеры:

```json
{
  "id": "ev:stdout:4",
  "source_file": "stdout.jsonl",
  "line": 4,
  "raw_type": "item.started",
  "ts": null,
  "session_id": "019d621d-620a-7d52-a76d-e45172a83603",
  "item_id": "item_1",
  "tool": "spawn_agent",
  "sender_thread_id": "019d621d-620a-7d52-a76d-e45172a83603",
  "receiver_thread_ids": [],
  "prompt": "Выполни короткий smoke test: ...",
  "status": "in_progress"
}
```

```json
{
  "id": "ev:subagent:23",
  "source_file": "subagents/019d621d-98e5-7da2-8c48-99a5267f1ad6.jsonl",
  "line": 23,
  "raw_type": "response_item.function_call",
  "ts": "2026-04-06T09:26:45.101Z",
  "session_id": "019d621d-98e5-7da2-8c48-99a5267f1ad6",
  "call_id": "call_poY5PltBnP6YViNfQgpr5GzQ",
  "tool": "exec_command",
  "arguments": {
    "cmd": "ping -c 1 127.0.0.1"
  }
}
```

## Связи

Ключевая часть модели это отдельный список `relations`.

Пример формы:

```json
{
  "type": "spawned_subagent",
  "from_event": "ev:stdout:5",
  "to_entity": "session:019d621d-98e5-7da2-8c48-99a5267f1ad6",
  "confidence": "exact",
  "evidence": [
    {"kind": "receiver_thread_id_match", "value": "019d621d-98e5-7da2-8c48-99a5267f1ad6"},
    {"kind": "filename_equals_session_id", "value": "019d621d-98e5-7da2-8c48-99a5267f1ad6"},
    {"kind": "forked_from_match", "value": "019d621d-620a-7d52-a76d-e45172a83603"}
  ]
}
```

### Типы связей

Минимально полезный набор:

- `session_log_of`
- `started_completed`
- `call_output`
- `spawned_subagent`
- `delegated_prompt`
- `waits_for`
- `returns_result`
- `closes`
- `summarizes`
- `duplicate_view`

## Сигналы для корреляции

### Сигналы высокой надёжности

- точное совпадение `item.id`
- точное совпадение `call_id`
- точное совпадение `thread_id`
- точное совпадение `receiver_thread_ids[*]` и `session_id`
- совпадение basename файла субагента и `session_id`
- совпадение `forked_from_id` и родительского `thread_id`
- совпадение `session_meta.id` с basename файла субагента
- точное совпадение текста prompt
- точное совпадение финального текста сообщения

### Сигналы средней надёжности

- совпадение набора фактов в тексте: команда, `exit code`, packet loss, latency
- близость по времени
- согласованность ролей parent/child

### Слабые сигналы

- просто похожий текст без общих идентификаторов

Такие связи лучше не сохранять как отдельные relation, если нет других подтверждений.

## Правила связывания внутри одного файла

### Жизненный цикл операции

`item.started` и `item.completed` связываются по одному `item.id`.

Тип relation:

- `started_completed`

### Вызов инструмента и его результат

`function_call` и `function_call_output` связываются по одному `call_id`.

Тип relation:

- `call_output`

### Дублирующие представления

Если есть `event_msg.agent_message` и рядом `response_item.message` с тем же текстом и почти тем же временем, это обычно не две разные операции, а два представления одного события.

Тип relation:

- `duplicate_view`

## Правила связывания между файлами

### Лог файла и сессия субагента

Если имя файла равно `subagents/<thread_id>.jsonl`, это сильный сигнал связи файла с сессией.

Тип relation:

- `session_log_of`

Дополнительное правило:

- если внутри файла встречается `session_meta` с `id`, не совпадающим с basename файла, такой `session_meta` нужно считать частью forked history или унаследованного контекста, а не открытием новой целевой сессии для этого файла;
- каноническим идентификатором session file остаётся id из имени файла, а совпадающий `session_meta.id` только усиливает уверенность связи.

### Создание субагента

Событие создания субагента в родительском логе связывается с дочерней сессией по признакам:

- `receiver_thread_ids[*] == child.session_id`
- `sender_thread_id == child.forked_from_id`
- `parent_thread_id == parent.thread_id`

Тип relation:

- `spawned_subagent`

Практическое ограничение:

- если в родительском потоке виден только `tool_name=spawn_agent`, но нет `receiver_thread_ids`, это ещё недостаточно для надёжной привязки к session file;
- такую запись можно использовать как слабый сигнал для timeline, но не как основание для relation `spawned_subagent`.

### Делегирование prompt

Prompt из `spawn_agent` в родительском логе может стать user message в дочернем логе.

Тип relation:

- `delegated_prompt`

### Ожидание результата

Вызов `wait` или `wait_agent` в родительском логе связывается с финальным сообщением дочерней сессии по признакам:

- child `thread_id` присутствует в `receiver_thread_ids`
- текст из `agents_states[child_id].message` совпадает с финальным сообщением child

Типы relation:

- `waits_for`
- `returns_result`

Уточнение по именам инструментов:

- на orchestration-level может использоваться имя `wait`, а на session-level прямой tool API может использовать `wait_agent`;
- поэтому при межслойной корреляции нельзя требовать точного совпадения `tool_name`, если остальные признаки связи указывают на одну и ту же операцию ожидания.

### Закрытие субагента

`close_agent` в родительском логе связывается с дочерней сессией по `receiver_thread_ids`.

Тип relation:

- `closes`

### Родительский summary и сырой результат дочерней сессии

Если родитель пишет сокращённый итог, а дочерний лог содержит сырой вывод команды, связь можно строить по совпавшим фактам.

Тип relation:

- `summarizes`

## Ограничения и edge cases

### Потенциальные дубли сообщений

На текущем этапе нужно считать допустимым, что одна и та же смысловая реплика субагента может быть видна в нескольких представлениях:

- `response_item.message`
- `event_msg.agent_message`
- `agents_states[*].message` в control-plane событиях родителя
- `task_complete.last_agent_message`

Практическое правило:

- пока не введена отдельная иерархия semantic message identity, такие повторы не нужно считать ошибкой парсинга сами по себе;
- при post-mortem анализе и проектировании correlation layer эти записи нужно рассматривать как потенциальные дубли одного сообщения;
- дедупликация откладывается до отдельного этапа, когда будет определена модель приоритетов между control-plane и session-detail событиями.

### Чужой `session_meta` внутри session file

Session file может содержать `session_meta` не только своей целевой сессии, но и чужой сессии из forked history.

Практическое правило:

- при открытии целевой дочерней сессии приоритет у basename файла;
- если встречается `session_meta.id`, совпадающий с basename файла, это подтверждение;
- если встречается другой `session_meta.id`, это не новая дочерняя сессия, а унаследованный контекст.

### Nested subagents и `parent_thread_id`

Для вложенных субагентов поле `parent_thread_id` в поздних строках session file может отражать корневой родительский поток run, а не реального непосредственного родителя.

Практическое правило:

- при построении дерева parent/child приоритет у ранних session identity-данных;
- поздние строки tool/message/meta полезны для ленты жизни агента, но менее надёжны для восстановления точной nested topology.
- сценарий `subagent -> subagent` нужно считать реальным и поддерживать как отдельный кейс дальнейшей доработки.

### `stdout.jsonl` не гарантирует готовый структурный слой

Название `stdout.jsonl` не означает, что файл всегда можно воспринимать как уже проверенный канонический JSONL-слой.

Практическое правило:

- относиться к нему как к исходному stdout-потоку;
- структурная валидность и нормализация должны быть отдельным шагом перед построением relations.

### Разные представления сообщений внутри session file

Внутри session file полезно различать:

- `response_item.message` и `response_item.reasoning`
- `event_msg.agent_message`
- прочие `event_msg.*`

Практическое правило:

- `event_msg.agent_message` чаще всего отражает человекочитаемую реплику агента;
- `response_item.message` и `response_item.reasoning` это соседний слой представления той же активности;
- их можно связывать relation типа `duplicate_view` или `same_semantic_message`, но не стоит безусловно считать одной и той же строкой журнала.

## Отложенные проблемы

Ниже перечислены проблемы, которые зафиксированы, но пока не исправляются в текущем этапе.

### 1. Потенциальные дубли в message-layer

Проблема:

- одна и та же реплика может приходить через несколько envelope-ов и несколько слоёв логирования.

Текущее решение:

- считать это допустимым поведением текущего этапа;
- не пытаться жёстко устранять дубли до появления явной модели semantic identity сообщений.

Отложенное действие:

- вернуться к задаче после стабилизации иерархии событий и parent/child model.

### 2. Nested subagent topology

Проблема:

- для вложенных субагентов возможно несоответствие между реальным непосредственным родителем и `parent_thread_id`, прокинутым в поздние session-level события.

Текущее решение:

- зафиксировать риск;
- отдельно спланировать исправление для сценария `subagent -> subagent`.

Отложенное действие:

- см. отдельный план в [event-processing-plan.md](/home/alko/develop/open-source/ai/infrastructure/codex-worker-rs/docs/event-processing-plan.md).

### 3. Переходы статуса после позднего импорта session file

Проблема:

- поздно импортированный `agent.session` или неполная дочерняя session может дать спорный status transition относительно уже известных terminal-state сигналов из control-plane.

Текущее решение:

- проблема зафиксирована;
- конкретная стратегия приоритета статусов пока не выбрана.

Отложенное действие:

- определить policy для terminal vs non-terminal статусов в отдельном плане.

### 4. Семантика `tool_counts` и `subagent_counts`

Проблема:

- на текущем этапе счётчики могут отражать количество event records или фаз операции, а не число логических вызовов.

Текущее решение:

- пока принимать эти счётчики как предварительные технические метрики;
- не интерпретировать их как точное число логических операций.

Отложенное действие:

- скорректировать модель счётчиков после формирования устойчивой иерархии событий и связей между call/result/control-plane слоями.

## Уровни уверенности

- `exact`: совпал структурный идентификатор или точный текст, который передаётся между событиями без преобразования
- `high`: прямого id нет, но есть согласованные parent/child признаки и совпадающий prompt или набор фактов
- `medium`: есть только несколько совпавших фактов и временная близость

Уровень `low` лучше не сохранять.

## Рекомендуемый порядок построения связей

Сначала выполняется первый проход по строгим признакам:

1. `item.started` -> `item.completed` по `item.id`
2. `function_call` -> `function_call_output` по `call_id`
3. `spawn_agent` -> child session по `receiver_thread_ids`
4. `subagent log file` -> `session` по имени файла и, если есть, по совпадающему `session_meta.id`
5. `wait` и `close_agent` -> child session по `receiver_thread_ids`
6. parent prompt -> child user message по точному совпадению текста

Потом выполняется второй проход по производным связям:

1. child final message -> `wait` result по совпадающему тексту
2. child raw output -> parent summary по совпавшим фактам
3. `event_msg.*` -> `response_item.*` как `duplicate_view` или `same_semantic_message`
4. отбрасывание или понижение уверенности для `session_meta`, не совпадающих с basename файла

## Пример на конкретной паре логов

Для родительского `stdout.jsonl` и дочернего `subagents/019d621d-98e5-7da2-8c48-99a5267f1ad6.jsonl` можно восстановить такую цепочку:

1. Родитель начал `spawn_agent`.
2. Родитель завершил `spawn_agent` и получил `receiver_thread_id=019d621d-98e5-7da2-8c48-99a5267f1ad6`.
3. Этот идентификатор указывает на дочерний лог `subagents/019d621d-98e5-7da2-8c48-99a5267f1ad6.jsonl`.
4. Prompt из `spawn_agent` стал user message в дочерней сессии.
5. Субагент вызвал `exec_command`.
6. Субагент получил output команды `ping -c 1 127.0.0.1`.
7. Субагент сформировал финальное сообщение.
8. Родитель через `wait` получил именно это финальное сообщение.
9. Родитель выполнил `close_agent` для того же `thread_id`.
10. Родитель выдал свой сжатый summary на основе результата дочерней сессии.

## Практическая рекомендация

Для дальнейшей обработки логов полезно строить не один список событий, а такой набор артефактов:

- нормализованный список `events`
- словарь `entities`
- список `relations`
- при необходимости отдельный `facts_index` для сравнения сокращённых и детальных сообщений

Такой формат позволяет:

- восстанавливать цепочки операций;
- строить UI для parent/child сессий;
- отдельно анализировать ошибки корреляции;
- не терять информацию, когда одно событие представлено в нескольких видах.
